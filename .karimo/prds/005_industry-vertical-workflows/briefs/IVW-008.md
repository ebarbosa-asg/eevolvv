# Brief: IVW-008 — Industry-aware onboarding form — fitness branch

## Context

The onboarding form (`/onboard/[token]`) is generic for all clients. Fitness gym owners need to provide gym software credentials, member count, and churn rate so eevolvv can actually start building the Month 1 automation (churn early-warning system). This task adds a fitness-specific branch to the onboarding form, sends an admin notification, and shows a Calendly booking CTA after submission.

## Codebase Reality

**Onboarding page:** `app/onboard/[token]/page.tsx` (95 lines) — server component. It fetches the token row from `onboarding_tokens` table, then fetches client info from `clients` table:
```ts
const { data: client } = await supabase
  .from('clients')
  .select('name, email, tier')
  .eq('id', tokenRow.client_id)
  .single()
```
Currently selects `name, email, tier` from clients. After IVW-003, `industry` will also be a column on `clients`. This page needs to also select `industry`.

**Onboarding form:** `app/onboard/[token]/OnboardingForm.tsx` (190 lines) — `'use client'` component. Current props:
```ts
interface OnboardingFormProps {
  token: string
  clientId: string
  tier: 'seed' | 'core' | 'evolve'
  defaultName?: string
}
```

**Form state** (line 19-34): `businessName, businessDescription, primaryGoal, topPains, existingTools, commChannel` for all tiers; `appType, integrationsNeeded, authRequired` for core+; `orgSize, techStack, keyStakeholders` for evolve.

**Form submission** (line 46): `PATCH /api/onboard/${token}` with the form state as JSON body.

**After submit** (line 70-80): Shows "You're in the queue." message with the build SLA.

**Admin notification:** `app/api/diagnostic/route.ts` (lines 211-260) has an inline admin notification email. For onboarding, there is presumably a route at `app/api/onboard/[token]/route.ts` (the PATCH handler referenced by the form). Read that file to see if it already sends admin notifications — if not, add it there.

**`NEXT_PUBLIC_CALENDLY_URL`** env var is set in `CLAUDE.md`: `https://calendly.com/hello-eevolvv`.

**`fitnessConfig.onboardingFields`** (from IVW-002):
- gymSoftware (select: Mindbody, Glofox, Zen Planner, Pike13, Other)
- softwareUsername (text, required)
- softwarePassword (password, required)
- apiKey (text, optional)
- memberCount (number, required)
- monthlyChurnRate (number, required)

## Gotchas

- `NEXT_PUBLIC_CALENDLY_URL` is a client-side env var. In `OnboardingForm.tsx` (a `'use client'` component), it's accessible as `process.env.NEXT_PUBLIC_CALENDLY_URL`. Do not use `CALENDLY_URL` without the `NEXT_PUBLIC_` prefix — it will be undefined in the browser.
- The password field sends the actual password in the PATCH request body to the server. The server stores it in `onboarding_tokens.responses` as JSONB. The admin notification email must NOT include the raw password — only indicate `credentialsPresent: true`. Security is the builder's responsibility to handle in the Supabase dashboard, not this task's scope.
- The `isFitness` check in `OnboardingForm` is computed from the `industry` prop, not from any form state. Compute it once at the top of the component: `const isFitness = industry === 'Fitness / Gym / Studio'`.
- The generic form fields (business name, description, primary goal, top pains, existing tools, comm channel) should still render for fitness clients — the fitness fields append after, not replace. This gives the eevolvv team full context.
- The `set` helper function (line 36 of current OnboardingForm) works by updating a field in the `form` state object. Add the new fitness fields to the initial `form` state object, then use `set('gymSoftware', value)` etc. — the same pattern as existing fields.
- Find the PATCH handler for `/api/onboard/[token]` before writing — its current behavior (updating the token status to 'completed' and saving responses) must be preserved. The admin notification is additive, fire-and-forget, wrapped in try/catch.
