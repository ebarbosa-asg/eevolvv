# Brief: IVW-007 — Industry-aware follow-up emails — fitness vocabulary

## Context

The three follow-up emails (sent at 24h, 48h, 72h after report generation) use identical generic copy for every lead. A fitness gym owner should receive emails that speak about members, churn, EFT failures, and specific eevolvv automations — not generic "operational headaches" language. This task adds industry awareness to all three email templates and wires the `industry` field through the send pipeline.

## Codebase Reality

**Email templates:**
- `emails/FollowUp1.tsx` — "Your report is waiting to be acted on." / "Seed tier ($950/yr) gets you a live, automated landing page in 72 hours."
- `emails/FollowUp2.tsx` — "Still thinking it over?" / social proof bullets about generic service business and solopreneur
- `emails/FollowUp3.tsx` — "Last chance to lock in your build." / generic urgency

**Current props** (all three files share the same shape):
```ts
interface FollowUp1Props {
  name?: string
  businessName?: string
}
```
No `industry` prop exists on any of them.

**Email send pipeline** — `app/api/diagnostic/route.ts` lines 263-274:
```ts
const rows = [
  { submission_id: submissionId, email, template: 'followup1', name: name ?? null, business_name: businessName ?? null, send_after: ..., status: 'pending' },
  { submission_id: submissionId, email, template: 'followup2', name: name ?? null, business_name: businessName ?? null, send_after: ..., status: 'pending' },
  { submission_id: submissionId, email, template: 'followup3', name: name ?? null, business_name: businessName ?? null, send_after: ..., status: 'pending' },
]
await supabase.from('email_queue').insert(rows)
```

**`email_queue` table** (migration 009): `id, submission_id, email, template, name, business_name, send_after, status, sent_at, error, created_at`. After IVW-003, it will also have `industry TEXT`.

**Where follow-ups are sent from:** The live send path is `app/api/cron/followup/route.ts`. This cron job queries the `submissions` table directly (not `email_queue`) and calls `sendFollowUpEmail()` from `lib/email-helpers.ts`. That helper renders the three email templates via `React.createElement(FollowUp1Email, { name, businessName })` — no `industry` prop exists yet. The `email_queue` table is populated by `diagnostic/route.ts` but nothing currently reads from it to send emails. The render call for follow-up emails lives in `lib/email-helpers.ts`.

Adding `industry: industry ?? null` is a new field addition, not a reference to an existing one. This populates the `email_queue` for forward-compatibility, but the live follow-up send path runs through the cron job (see Change 2).

### Change 2 — `app/api/cron/followup/route.ts` + `lib/email-helpers.ts`

The live follow-up send path does NOT read from `email_queue`. The cron job at `app/api/cron/followup/route.ts` queries the `submissions` table directly and calls `sendFollowUpEmail()` from `lib/email-helpers.ts`. That function renders templates via `React.createElement(FollowUp1Email, { name, businessName })` — with no `industry` prop currently.

**Step 2a — `app/api/cron/followup/route.ts`:**

Add `industry` to the Supabase SELECT query (currently around lines 20–22):
```ts
// Before:
.select('id, email, name, business_name, created_at, followup_sent_at')

// After:
.select('id, email, name, business_name, created_at, followup_sent_at, industry')
```
Then pass `industry` from the fetched row to `sendFollowUpEmail()`:
```ts
// Before:
await sendFollowUpEmail({ email, name, businessName })

// After:
await sendFollowUpEmail({ email, name, businessName, industry: row.industry ?? undefined })
```

**Step 2b — `lib/email-helpers.ts`:**

Update `sendFollowUpEmail()` signature to accept `industry?: string`:
```ts
// Before:
async function sendFollowUpEmail({ email, name, businessName }: { email: string; name?: string; businessName?: string })

// After:
async function sendFollowUpEmail({ email, name, businessName, industry }: { email: string; name?: string; businessName?: string; industry?: string })
```
Update all three `React.createElement()` calls to pass `industry` through:
```ts
// Before:
React.createElement(FollowUp1Email, { name, businessName })

// After:
React.createElement(FollowUp1Email, { name, businessName, industry })
```
Apply the same change to the `FollowUp2Email` and `FollowUp3Email` createElement calls.

## Gotchas

- The live follow-up send path is `app/api/cron/followup/route.ts` → `lib/email-helpers.ts` → `React.createElement(FollowUpNEmail, ...)`. The `email_queue` table is populated but nothing reads from it to send emails. Both the cron route and email-helpers.ts must be modified — without these changes, `industry` will never reach the templates even though diagnostic/route.ts populates the queue correctly.
- The email templates use `@react-email/components` for layout — they render to HTML via `render()`. The fitness copy blocks must use the same `<Text>` and `<Section>` components as existing copy to maintain email client compatibility. Do not use raw `<p>` tags.
- All three email templates have identical import structure: `Html, Head, Body, Container, Section, Text, Heading, Button, Hr, Preview, Font` from `@react-email/components`. Add `import { fitnessConfig } from '@/lib/industries'` only if using the config values directly; otherwise hardcode the comparison string to avoid email template bundle complexity.
- The fitness copy uses `→` and `↳` characters for bullet formatting — these are part of the eevolvv design language and render correctly in email clients that support Unicode. They are already used in FollowUp2's social proof block.
- `BASE_URL` is already defined in each email file as `process.env.NEXT_PUBLIC_BASE_URL ?? 'https://eevolvv.com'`. Use it for all href values.
