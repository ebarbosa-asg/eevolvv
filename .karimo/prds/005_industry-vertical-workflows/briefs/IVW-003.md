# Brief: IVW-003 — Supabase migration — industry column on clients table

## Context

The `clients` table has no `industry` column, which means the OS dashboard cannot filter clients by vertical, and the onboarding flow cannot branch on industry. This migration adds the column with an index and is a pure SQL file — no application code changes.

**Next migration number is 010.**

**`clients` table current columns** (established before this migration set, with additions from 006):
- Pre-existing: name, company, email, phone, business_type, contract_value, stage, health, notes, submission_id, created_at, updated_at
- Added in 006: email, stripe_customer_id, tier, churn_risk, last_portal_visit_at

**`onboarding_tokens` table** (created in 006): has `client_id` FK to clients. The token row is what the onboarding page fetches to look up client info. This is where `industry` will be read when the onboarding form needs to branch.

**`submissions` table** already has `industry TEXT` (migration 001 line 15). Every submission stores industry. The FK between clients and submissions goes through `clients.submission_id` (a column that exists pre-migration-set).

**`email_queue` table** (migration 009): columns are `id, submission_id, email, template, name, business_name, send_after, status, sent_at, error, created_at`. No `industry` column. This migration should also add `industry TEXT` to `email_queue` so follow-up email sends can branch on vertical.

## What to Build

Create one file: `supabase/migrations/010_clients_industry_column.sql`

The migration must:

1. **Add `industry` column to `clients` table:**
   ```sql
   ALTER TABLE clients ADD COLUMN IF NOT EXISTS industry TEXT;
   ```

2. **Add index on `clients.industry`:**
   ```sql
   CREATE INDEX IF NOT EXISTS idx_clients_industry ON clients (industry);
   ```

3. **Add `industry` column to `email_queue` table** (needed by IVW-007 so follow-up sends know the industry):
   ```sql
   ALTER TABLE email_queue ADD COLUMN IF NOT EXISTS industry TEXT;
   ```

4. **Optional backfill from submissions** — if a client has a `submission_id`, copy industry from the linked submission. Write this as a safe UPDATE with a JOIN, wrapped in a comment explaining it's a best-effort backfill:
   ```sql
   -- Backfill: copy industry from linked submission where known
   UPDATE clients c
   SET industry = s.industry
   FROM submissions s
   WHERE c.submission_id = s.id::text
     AND s.industry IS NOT NULL
     AND c.industry IS NULL;
   ```

5. **Standard migration header** following the pattern from 006:
   ```sql
   -- ============================================================
   -- Migration 010 — Industry column on clients + email_queue
   -- PRD: industry-vertical-workflows
   -- Created: 2026-05-09
   -- ============================================================
   ```

## Gotchas

- The `clients` table was created before this migration set began — it exists in production but has no corresponding `CREATE TABLE` in these migration files. That is expected and documented in migration 006 header. Do not attempt to recreate or redefine it.
- `clients.submission_id` is a `TEXT` column (not UUID) based on how it's referenced in migration 006. The backfill uses `s.id::text` cast to match. If the cast fails in your environment, the backfill can be omitted — it is non-critical.
- The `email_queue` addition is important: without `industry` in that table, the cron job that sends follow-up emails (IVW-007) cannot pass industry to the email templates. Add it here rather than in a separate migration.
- Do NOT add `industry` to the `submissions` table — it already exists there (migration 001 line 15).
- Do NOT add RLS policies for the new columns — the existing table-level policies (service role only) already cover all columns.
- This migration should be applied to Supabase via the CLI (`supabase db push`) or the Supabase dashboard SQL editor. The agent writing application code (IVW-006, IVW-007, IVW-008) depends on this column existing at runtime.
